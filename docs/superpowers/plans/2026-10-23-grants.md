# N2 Grants (build spec 3.8, build list #17, launch acceptance "a district opens next year's grant cycle ...")

Lane b, first module. Status: built (see "Done" at the end).

## Goal

Done when (spec): a district opens next year's cycle, a club submits, the district approves with notifications at
each step, pays, receives the report and closes the grant. Web layers only (API + admin); the app gets endpoints.

## What exists

- Nothing for district grants. RIZones (reference/) has no grants module either. `rotary_projects*` carries Global
  Grant / CSR funding fields (TRF grants), not district grants: left alone.
- Reused: `ScopeWriteGuardMiddleware.AllowedAsync` (who manages a club / district), `IAuditLogService` +
  `AuditMiddleware`, `IEmailService.SendScopedEmailAsync` (Brevo, 30 s timeout, email_log), the mobile bell
  (`MobileNotificationFeedService`, new leg "grant"), `FeatureGate` (Kind.Flagged "grants"), `IYearTableResolver`,
  admin `components/FeatureGate.tsx`, skeleton primitives, `getClubMembersForAttendance` for the member picker.
- "District on ROW" signal: a district tenant row in `tenant_subscriptions` (`fk_club_id = 0`, set in
  Settings > Tenants). No row = not on ROW = light mode for its clubs, and its district admins cannot open cycles.

## Tables (DatabaseInitializer.Grants.cs, schema.sql)

grant_cycles (one per district per Rotary year: DDF budget, max request, min qualified members, window, report
due date, rules text, draft/open/closed) · grant_applications · grant_application_lines (income, expense, partner)
· grant_application_members (qualified members) · grant_attachments (files in App_Data/grant-files, not wwwroot)
· grant_events (every transition and comment) · grant_payments (recorded disbursements) · grant_notifications
(in-app feed rows + email outbox) · grant_project_light (light mode: grant amount + report date per project).

## States and who moves them

draft (club only, before the spec's 10) -> submitted -> information_requested <-> information_provided,
adjustment_requested -> (club resubmits) submitted, approved (amount, within the cycle's DDF budget) -> paid (first
recorded payment) -> report_submitted -> closed; rejected (reason required); cancelled; report_submitted -> paid
when the district returns the report. Club actions only on club routes, district actions only on district routes.
Every transition: grant_events row, audit_log row, in-app + email notification to the applicant, the club's admins
and the district's admins (minus the actor).

## Endpoints

District (district managers only, reads included): cycles GET/POST/PUT, cycles/{id}/cashflow, cycles/{id}/export
(CSV), applications GET (cycle, status, archived), applications/{id} GET, actions/{action}, comments, payments,
attachments/{id} GET. Club (club managers only): grants GET (overview + light mode flag), applications POST,
applications/{id} GET/PUT, actions/{action}, comments, attachments POST/DELETE/GET, light GET, light/{yearId}/{projectId} PUT.

## Pages

/district-admin-dashboard/grants (cycles, cash flow, status counts, list, archive, CSV) and /grants/[applicationId];
/club-admin-dashboard/grants (applications or light mode) and /grants/[applicationId] (form, actions, report).

## e2e

kb/tools/grants_e2e.py: flag off = 404; full flow submit -> info -> adjustment -> approve -> pay -> report -> close;
validation (reason required, budget, over-payment, qualification); role gating; club B cannot see club A's
application; notifications and audit rows per transition; cash flow, CSV, archive; reject and cancel paths;
light mode. Cleans up its rows (audit_log is append-only by design and keeps its rows).

## Left for the app

Same endpoints; feed type "grant" (deep link type grant_application, entity id = application id).

### Open issues
1. "District on ROW" = a district tenant row (tenant_subscriptions, fk_club_id = 0). The prod copy has 0 tenant
   rows, so until a SuperAdmin saves each district in Settings > Tenants every district counts as not on ROW: its
   admins cannot open cycles and its clubs get light mode. Needs the user's confirmation that this is the signal.
2. The prod copy has no district-level Admin role rows; a district needs one before it can run grants (the e2e
   adds a temporary one).
3. Grant emails go out only where BackgroundJobs:Enabled is on (production default; off in Development). They are
   transactional and are not deducted from email credits: confirm.
4. The API sends no X-Content-Type-Options header globally; grant downloads set it themselves.
5. The web console has no in-app bell for these notifications: admins get the email and the page history; the
   in-app copy shows in the app's bell (feed type "grant").
6. Pages were type-checked and design-checked, not opened in a browser (next dev is not allowed in lanes).
7. The lanes share one scratchpad folder: lane d overwrote this lane's api.log and jwt.txt once; lane-specific
   subfolders fixed it here.
